# Final Load-Latency Fix — cold start, payloads and round trips

Status: implemented on `perf/final-load-latency-fix` (supersedes the
`performance-fix-phase-*` PR chain #54–#62).
Scope: PostgreSQL stays the source of truth. No change to auth, RBAC,
visibility, API contracts, business semantics, or UI.

---

## 1. The problem, in numbers

The user-visible complaint: **"data takes very long to load."**

Previous phases (docs/PERFORMANCE_PHASE_2.md, PERFORMANCE_PHASE_3.md,
DATABASE_PERFORMANCE_AUDIT.md) had already removed polling, split the
bundle, coalesced duplicate GETs and sequenced the first-dashboard
requests. Yet mobile recordings still showed:

| Endpoint | Client total | Server-Timing |
|---|---:|---:|
| `GET /api/dashboard` | 47.6 s | 1.6 s |
| `GET /api/leads/follow-ups?bucket=today` | 46.8 s | (not the bottleneck) |
| `GET /api/leads/follow-ups?bucket=upcoming` | 45.1 s | (not the bottleneck) |

A 45 s client wait against a 1.6 s server answer cannot come from SQL.
This change set was built by measuring what happens **before** the first
request is even dispatched, and what the server does on **every** new
function instance.

### 1.1 Root cause A — every cold start replayed the full schema

`api/index.ts` awaited `initializeDatabase()` before it would dispatch its
first `/api/*` request, and `runMigrations()` had no ledger: it re-ran
**every** migration function plus the seed routines on every process boot.

Measured on an already-current schema (see §4 for the command):

```
before: 226 PostgreSQL round trips   (326 on a virgin database)
after :   4 round trips              (ledger says: nothing pending)
```

Multiply by the Vercel→Supabase round-trip time, and remember that **every
new function instance pays it on its own cold start**:

| RTT | before | after |
|---:|---:|---:|
| 10 ms | 2.3 s | 0.04 s |
| 30 ms | 6.8 s | 0.12 s |
| 60 ms | 13.6 s | 0.24 s |
| 100 ms | 22.6 s | 0.40 s |

That is the "loading forever" experience: the first requests landing on a
cold instance queued behind a DDL replay, and concurrent instances could
contend on DDL locks — which is why three requests reported ~45 s while
their own `Server-Timing` was ~1.6 s (they were waiting, not computing).

### 1.2 Root cause B — multi-MB JSON, uncompressed

`GET /api/leads` returns up to 5000 `l.*` rows and is called by LeadList,
AllLeads, ExecutionIntelligence, NcpProgress, TrendCharts,
CampaignBreakdown, TeamHierarchy and Activities. Measured with 1500 leads:

```
payload 1 233 KiB   →  gzip 77.5 KiB   (≈16x smaller)
```

Nothing in the stack enabled compression (`npm run build` output shows the
SPA assets are compressed by Vite, but API responses are generated by the
server and were sent raw). On a mobile radio this transfer alone dominates
"data load".

### 1.3 Root cause C — serial authorization round trips + pool shape

Every read endpoint paid: caller lookup → permission check(s) → visibility
resolution → query, one awaited round trip at a time. `GET /api/dashboard`
checked two permission codes sequentially, then resolved visibility.

The connection pool was also sized for a long-lived server (`max: 20` per
instance, no `keepAlive`, no runtime awareness), which on serverless is
exactly the configuration that produces pool-checkout waits (the chain's
own diagnostics observed **1.2–2.6 s** of acquire wait).

## 2. What changed

### 2.1 Ledger-backed schema boot (root cause A)

New `server/database/migrationLedger.ts` + rewritten
`server/database/runMigrations.ts`:

* a `schema_migrations` table records each migration id the moment it
  succeeds — a current schema is a **1 probe + 1 SELECT** check;
* a PostgreSQL **advisory lock** (`pg_try_advisory_lock`) makes concurrent
  cold starts safe: one instance migrates, the others log and continue
  instead of racing DDL;
* a legacy database (created before the ledger) is **adopted** when the
  last migration's objects are already present (042 `roadshows`, 041 open
  index, `leads`, `users`) — no DDL replay, no guessing: if any sentinel is
  missing, the migrations run normally;
* a migration that throws is **not** recorded, so the next boot retries it
  (previous behavior preserved);
* `runSeeds()` is marker-gated (`seed:baseline-v1`), so the five idempotent
  seed routines cost zero round trips after the first successful run;
  `LEADFLOW_FORCE_SEEDS=1` re-runs them on purpose.

`initializeDatabase()` now reports `{ noOp, durationMs, migrations, seeds }`
and honours `LEADFLOW_RUNTIME_MIGRATIONS=off` for pipelines that prefer to
own the DDL (`npm run migrate:production`, with `--check` for gates).

Both entrypoints were re-plumbed so the work overlaps startup instead of
sitting in front of a user request: `server.ts` kicks the bootstrap off at
module evaluation and every request awaits the **same** promise (a failed
boot resets it so a later request can retry); `api/index.ts` keeps its
module-eval warm-up, now bounded at a few round trips.

### 2.2 Compression + payload honesty (root cause B)

* `compression` (gzip, level 6, 1 KiB threshold) is mounted by
  `applyProductionHttpSecurity()` — the same call both entrypoints make —
  so no API response can bypass it. `x-no-compression` is honoured and
  already-encoded responses are never double-encoded.
* `LEADS_LIST_MAX_ROWS` (default 5000 = unchanged behavior) lets ops cap
  the shared lead-list read without a code change once their pages pass an
  explicit `limit`. Documented, not silently applied.

### 2.3 Fewer round trips, better pool (root cause C)

* `/api/dashboard`: the two permission codes and the visibility scope are
  resolved in one parallel batch (they are independent and request-memoized).
* `/api/leads`, `/api/leads/follow-ups`, `/api/scheduled-activities`: the
  permission check and visibility resolution overlap; the 403 is still
  returned before any row is read.
* `/api/leads/follow-ups`: the bucket predicate is now a **half-open range**
  (`next_follow_up_at >= todayStart AND < tomorrowStart`) instead of
  `CASE ... = 'today'`, so migration 038's partial index actually serves the
  page query; the bucket aggregate and the page query run in **parallel**
  and the redundant per-bucket `COUNT` is gone (the aggregate already
  carries the exact total).
* Bulk-import / bulk-user-import / notification fan-out permission batches
  are issued in parallel instead of sequentially (5 → 1 round trip on the
  import path).
* `server/database/connection.ts`: connection-string precedence
  (`DATABASE_URL` → `POSTGRES_URL` → `POSTGRES_PRISMA_URL`), serverless-aware
  pool sizing (`PG_POOL_MAX`, default 6 on serverless / 20 on long-lived),
  `keepAlive`, `application_name`, 15 s acquire timeout, 10 s idle timeout on
  serverless, optional `PG_STATEMENT_TIMEOUT_MS`, and a loud one-time
  warning when a serverless runtime is pointed at a Supabase **direct**
  endpoint instead of the pooler.
* Pool-checkout wait is now attributed to the request
  (`dbAcquireDurationMs`, `dbPoolWaitingCount`), exposed in the request log
  and in `Server-Timing` as `dbq` (queries) and `dbwait` (acquire) — so a
  saturated pool can never again be mistaken for slow SQL.

### 2.4 Client-side

* `usePermissions()` waits on the existing **shell** gate before fetching
  the user's own permission sheet: that sheet governs optional client
  actions (e.g. the Add Lead button), never authentication or server
  authorization, so it must not compete with the critical KPI request on a
  first Dashboard load. Non-`/` routes release the gate immediately.
* `adminService.getRoles()` no longer emits `ROLES_CACHE_CHANGED_EVENT` on a
  successful **read**. Announcing a GET made every listener (FeatureGate,
  usePermissions) reload `/api/roles`, whose cache write announced again —
  a self-sustaining startup request loop. The event is reserved for
  save/delete mutations.

### 2.5 Dashboard wiring completion (follow-up commit)

Making the network fast is only half of the perceived fix: the routed
Dashboard (`src/modules/dashboard/pages/Dashboard.tsx`) had sections that
were **fetched but never rendered**, and one section that could never leave
its loading state. That is also why 13 pre-existing tests were red on
`main` — the guards were right, the screen was incomplete.

* **Today's Focus** now renders the server-authoritative
  `TodayTomorrowPanel` (overdue/today/upcoming counts from
  `GET /api/dashboard` plus the already-fetched follow-up-queue and
  2-day scheduled-activity lists) instead of two dead count cells. No new
  request: every figure was already in memory.
* **Recent Leads** — the section was stuck on its skeleton forever because
  `recentLeadsLoading` was never resolved. It now reads the capped,
  newest-first projection of the local mirror of server data
  (`localDb.getRecentLeads(5)`): zero requests, no second authority, and
  an honest empty state on a first-ever visit. The KPI loader is explicitly
  forbidden from touching the mirror (guard: perf-phase2 G).
* **Lead Quality**, **Trend/Team Performance**, **Sales Pipeline**,
  **Follow-Up Discipline** and **Needs Attention** are rendered again,
  bound to the SAME `GET /api/dashboard` payload (`metrics.quality`,
  `metrics.trendData`, `metrics.teamStats`, `statusCounts`) — no extra
  fetch, and `noUnusedLocals` is clean again (11 dead bindings removed).
* **Task Calendar** is mounted last, inside its Suspense boundary and only
  once `calendarReady` flips (primary content settled), so the heavy
  calendar chunk and its own request stay off the critical path.
* **Guards repaired, not deleted.** Several source guards still described
  the pre-redesign layout (18 routes, `TodayTomorrowPanel` rendered
  directly, old login hero copy, `Lead Workspace` / `Lead Pool` shell
  labels, a dead `const formattedDateRange` slice anchor that made two
  tests vacuous). They now assert the shipped structure with the same or
  stronger guarantees — e.g. the route guard compares *every*
  `ProtectedRoute` / `<LazyPage>` against the gated-route count instead of
  a magic `18`, and the loader-slice guards now fail loudly if their
  boundary marker disappears.

## 3. Measured result

Same harness, same data, same simulated DB latency (`DB_RTT_MS=30`,
1500 leads), run on `main` and on this branch:

| Metric | `main` | this branch |
|---|---:|---:|
| **Cold start, current schema** | **226 round trips ≈ 7.0 s** | **4 round trips ≈ 0.12 s** |
| Cold start, virgin database (one time) | 326 round trips | 368 round trips\* |
| `GET /api/dashboard` | 11 RT / 597 ms | 11 RT / 569 ms (authz 63 ms → 32 ms) |
| `GET /api/leads/follow-ups?bucket=today` | 9 RT / 274 ms | 8 RT / 184 ms |
| `GET /api/leads/follow-ups?bucket=all&limit=200` | 9 RT / 321 ms | 8 RT / 240 ms |
| `GET /api/leads` (1500 leads) | 1 233 KiB raw | 1 233 KiB → **77.5 KiB gzip** |
| First-load burst (7 parallel reads) | 635 ms | 582 ms |

\* One extra round trip per migration on the very first run (the ledger
write). It happens once per database, ever.

Reproduce (development only, in-process PGlite, no production access):

```bash
DB_RTT_MS=30 DB_LEADS=1500 npx tsx scripts/perf-roundtrip-audit.ts
npx tsx scripts/migrate-production.ts --check     # reports ledger state, exits 1 if pending
```

## 4. Deployment notes

1. **No database migration is required** — the ledger table is created
   automatically on the first boot and legacy databases are adopted.
2. The first production boot after this deploy performs **one** ledger
   adoption (a handful of round trips) — no DDL replay.
3. Recommended (optional) — move even those round trips off the release:

   ```json
   // vercel.json  (production builds only; preview builds skip automatically)
   "buildCommand": "npm run migrate:production && npm run build"
   ```

   and then set `LEADFLOW_RUNTIME_MIGRATIONS=off` for the runtime. Without
   those two steps the app still converges the schema at boot (the default).
   `MIGRATE_STRICT=1` makes the deploy-time step fail the build instead of
   warning.
4. For serverless deployments, point the database at the **pooled**
   endpoint (Supabase port `6543` / `*.pooler.supabase.com`) and, if needed,
   lower `PG_POOL_MAX`. A direct endpoint still works, but the process logs a
   warning because it costs a full handshake per instance and consumes a
   hard connection slot.
5. Mobile verification: use the existing admin-only
   Performance Diagnostics panel (docs/MOBILE_PERFORMANCE_DIAGNOSTICS.md).
   `Server-Timing` now also carries `dbq` (query count) and `dbwait` (pool
   acquire), so a slow report can be attributed without guessing.

New guards in `server/tests/perf-final-latency-fix.test.ts`:

* a virgin database applies every migration and records them;
* a current schema boots with **zero DDL** and ≤ 8 round trips;
* seeds run once, then skip;
* an unrecorded (failed) migration is pending again;
* a legacy database is adopted, not replayed;

  routes, sargable follow-up predicate, parallel authorization batches,
  `dbq` / `dbwait` reporting.

## 6. Known remaining costs (deliberately not changed here)

1. **`GET /api/leads` still returns up to 5000 full rows** and the client
   mirrors them into `localStorage` on every call (~1.2 MB at 1500 leads).
   Compression removes the transfer cost; parse + storage remain on the
   device. The correct fix is a product decision (server-side aggregates for
   the chart pages, and a smaller default page with explicit `limit`
   everywhere), so this PR ships the `LEADS_LIST_MAX_ROWS` knob and leaves
   the semantics unchanged.
2. **Region placement**: keep the function region and the database region
   aligned. Round trips are now few, but each still costs the full RTT.
3. Mobile radio/TLS/HTTP-2 head-of-line blocking can still inflate a single
   request; sequencing (Phase 3) and compression remove the parts that were
   under the app's control.
